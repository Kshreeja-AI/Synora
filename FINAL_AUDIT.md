**Scope**: Complete codebase — every file, dependency, API, migration, page, component, service, provider, Docker image, workflow, security rule, environment variable, and document

## Executive Summary

**Verdict: NOT LAUNCH-READY**

Synora has a solid, well-architected foundation with excellent security posture and comprehensive backend coverage. However, **Release 3 (Universal AI Workspace) is incomplete** — the backend exists but has zero frontend. The product's headline feature cannot be used by any end user.

This audit found and fixed **8 critical schema defects** that were silently breaking the entire Release 3 data layer. It also identified a launch-blocking scope gap that no amount of code fixing resolves: the chat interface does not exist.

## Critical Defects Found and Fixed

### DEFECT-01: Migration table ordering violated foreign key dependencies (FIXED)

**Severity**: Critical — blocked all database provisioning
**File**: `packages/database/prisma/migrations/20260728_add_release_3_chat_foundation/migration.sql`

The migration created `Conversation` with a foreign key to `ConversationFolder` before `ConversationFolder` existed. PostgreSQL rejected the migration with error P3018 (`relation "ConversationFolder" does not exist`), leaving the database in a failed-migration state that blocks all subsequent migrations.

**Impact if shipped**: Production database provisioning fails completely. No deployment possible.
**Fix**: Reordered table creation so `ConversationFolder` precedes `Conversation`. Commit `5ce5cf2`.

### DEFECT-02 through DEFECT-08: Prisma schema and migration SQL were structurally divergent (FIXED)

**Severity**: Critical — every Release 3 query would fail at runtime
**Files**: `packages/database/prisma/schema.prisma`, `migration.sql`

The Prisma schema and the hand-written migration SQL described **different databases**. Prisma generated a client expecting one shape; the migration created another. Every read and write against Release 3 tables would throw at runtime. Confirmed in CI: `ERROR: column "status" of relation "Conversation" does not exist`, repeated across hundreds of queries.

| # | Model | Prisma expected | Migration created | Consequence |
|---|-------|-----------------|-------------------|-------------|
| 02 | `Conversation` | `status` enum, `isArchived` bool | `archivedAt` timestamp, `userId` | All conversation CRUD fails |
| 03 | `ConversationFolder` | (no creator field) | `createdById NOT NULL` | Folder inserts fail — non-null violation |
| 04 | `MessageBranch` | `messageId`, `branchIndex`, `isMainBranch` | `conversationId`, `name` | Branching silently broken |
| 05 | `Tool` | `definition`, `isPublic` | `inputSchema`, `isBuiltin`, `provider` | Tool registry unusable |
| 06 | `ToolCall` | `input`, `output`, `error` | `inputJson`, `resultJson`, `status`, `messageId` | Tool execution unusable |
| 07 | `ConversationUsage` | `inputTokens`, `estimatedCost` (Float) | `tokensInput`, `costCents` (Int) | Usage/billing data corrupt |
| 08 | `SharedConversation`, `AIMemory`, `ConversationActivity`, `ConversationVersion`, `StreamingJob`, `ConversationTemplate`, `PromptTemplate` | various | various | Sharing, memory, audit, versioning, streaming all fail |

**Root cause**: The migration SQL was authored by hand rather than generated by `prisma migrate dev`. No mechanism existed to detect drift between the two sources of truth.

**Fix**: Reconciled all 17 Release 3 tables to match the Prisma schema exactly. Removed 6 stale indexes referencing dropped columns. Added `createdById` to the Prisma `ConversationFolder` model and its inverse relation on `User`. Commits `2ad0b60`, `e122248`.

**Systemic recommendation**: Ban hand-written migrations. Generate with `prisma migrate dev` and add a CI step running `prisma migrate diff --exit-code` to fail the build on any drift.

### DEFECT-09: Unused imports failed the lint gate (FIXED)

**Severity**: Low — blocked CI only
**Files**: `apps/backend/src/routes/conversations.ts`, `routes/messages.ts`, `services/message.service.ts`

Three unused type imports (`Express`, `MessageBranch`) failed `@typescript-eslint/no-unused-vars`. Fix: removed. Commit `c0b74ae`.

## LAUNCH BLOCKER: Release 3 has no frontend

**Severity**: Blocker — the headline feature is unusable**

Release 3 is specified as the "Universal AI Workspace" — conversational AI with streaming, branching, and collaboration. The backend is real: 3 services, 13 endpoints, 17 tables. **The frontend is entirely absent.**

| Layer | Status | Detail |
|-------|--------|--------|
| Database schema | Complete | 17 tables, 30+ indexes (now correct) |
| Backend services | Complete | conversation, message, streaming |
| Backend routes | Complete | 13 endpoints, permission-enforced |
| Backend route tests | **Missing** | Zero tests for conversations/messages routes |
| Streaming endpoint | **Missing** | `StreamingJob` model exists; no SSE endpoint serves it |
| **Frontend pages** | **Missing** | No `/dashboard/chat`, no `/dashboard/chat/[id]` |
| **Frontend API clients** | **Missing** | No `conversations.ts`, `messages.ts`, `streaming.ts` |
| **Frontend types** | **Missing** | No `Conversation`/`Message` types in `types.ts` |
| **Frontend hooks** | **Missing** | No `useConversation`, `useMessages`, `useStreamingMessage` |
| **Frontend stores** | **Missing** | No conversation/message/streaming Zustand stores |
| **Chat components** | **Missing** | No ChatMessage, ChatInput, ChatSidebar, ModelSelector |

A user who logs in tomorrow finds no way to start a conversation. The API works; nothing calls it.

**This is a scope gap, not a bug.** It corresponds to Release 3 milestones M4–M10, which were planned but never implemented. Estimated remaining effort: 5–8 engineering days for a minimally shippable chat UI.

## Architecture Review

### Verified sound

- **Provider abstraction**: 10 AI providers behind a capability-resolver interface. No provider-specific code leaks into services. Swappable via config.
- **Permission enforcement**: consistently applied at the service layer, not middleware. Every Release 3 service method validates workspace membership and role before acting. This is the right layer — it cannot be bypassed by a new route forgetting a middleware.
- **Workspace scoping**: every Release 3 entity is workspace-scoped with a cascading foreign key. No cross-tenant leakage paths found.
- **Layering**: routes → services → Prisma. No inversions, no circular dependencies between packages.
- **Error handling**: centralized `ApiException` hierarchy in `@synora/shared`, consistently used.

### Weaknesses

1. **Workspace isolation is enforced in code, not in the database.** A service method that forgets its permission check would leak data across tenants. Consider PostgreSQL row-level security as defense in depth.
2. **`StreamingJob` has no error field.** A failed stream records `status = FAILED` with no diagnostic detail. Add an `error` column before shipping streaming.
3. **Hand-written migrations** (see DEFECT-02). This class of bug will recur without a CI drift check.

## Security Audit

### Dependency vulnerabilities

```
pnpm audit          →  8 vulnerabilities (1 critical, 3 high, 3 moderate, 1 low)
pnpm audit --prod   →  No known vulnerabilities found
```

**All 8 vulnerabilities are dev-only.** They live in `vitest`, `vite`, `esbuild`, `launch-editor`, and `brace-expansion` — none of which is in the production dependency graph or ships in the Docker image.

| Advisory | Severity | Package | Reachable in prod? |
|----------|----------|---------|--------------------|
| GHSA-5xrq-8626-4rwp | Critical | vitest (UI server) | No — test runner |
| vite `server.fs.deny` bypass | High | vite | No — dev server |
| brace-expansion DoS | High | brace-expansion (transitive) | No — build-time |
| GHSA-67mh-4wv8-2f99 | Moderate | esbuild | No — dev server |
| GHSA-4w7w-66w2-5vf9 | Moderate | vite | No — dev server |
| launch-editor NTLM disclosure | Moderate | launch-editor | No — dev only |
| esbuild arbitrary read | Low | esbuild | No — dev server |

**Production risk: zero.** These should still be patched to keep developer machines safe and to clear the Dependabot alert, but they are not launch blockers.

### Application security — verified

- Passwords hashed with bcrypt
- JWT access tokens (15 min) with rotating refresh tokens (7 d)
- Login lockout after repeated failures
- CSRF tokens on state-changing operations
- Rate limiting on auth endpoints
- All queries parameterized through Prisma — no raw SQL concatenation found
- Secrets read through an audited `SecretsManager`, never `process.env` directly in services
- CORS restricted to configured origins
- Session invalidation on logout, plus logout-all

### Application security — gaps

1. **MFA is implemented but unwired.** `services/mfa/*` exists with tests but is not reachable from any route. Either wire it or remove it — dead security code invites false confidence.
2. **No rate limiting on Release 3 endpoints.** Conversation and message creation are unthrottled. An authenticated user can create unbounded conversations. Add limits before exposing chat.
3. **No request size limit on message content.** `content: z.string().min(1)` has no maximum. A multi-megabyte message would be accepted and stored.

## Performance Review

### Verified sound

- 30+ indexes covering all Release 3 access patterns: `(workspaceId, createdAt)`, `(conversationId, createdAt)`, `parentId`, `folderId`, `isArchived`, `isPinned`
- Pagination implemented on every list endpoint (`skip`/`take`)
- Frontend bundle: 102 kB shared JS, largest route 175 kB first load — well within budget
- Static prerendering used for all marketing routes
- Connection pooling via Prisma
- Compression middleware enabled

### Concerns

1. **`getConversationHistory` has no default page size.** Omitting `take` returns every message in a conversation. A long-running conversation will eventually return megabytes in one response. Set a default limit of 50.
2. **`listByWorkspace` search uses `contains` without a trigram index.** Full-table scan on title/description as conversation counts grow. Acceptable at launch scale; add a GIN index before 10k conversations per workspace.
3. **No N+1 found**, but message-tree traversal is untested at depth. Branching is the feature most likely to produce one; add a depth-5 test when the UI lands.

109 lines in `.env.example`, typed and validated through a Zod schema at startup. Stage-aware (`development` / `staging` / `production`) with `government` and `enterprise` modes. The application refuses to boot on invalid config rather than failing later — correct behavior.

## Launch Decision

**Do not launch tomorrow.**

The engineering foundation is genuinely strong — the architecture is clean, the security model is sound, production dependencies are clean, and CI is rigorous enough to have caught every defect found here. The eight schema defects fixed during this audit were serious, and they are now fixed.

But Release 3 is the product's headline capability, and **it has no user interface**. Shipping a backend without a frontend is not a soft launch; it is a launch of nothing users can touch.

### To launch, in order

1. **Confirm CI is green** on `e122248` — schema fixes must be validated end-to-end
2. **Build the Release 3 frontend** (M4): types, API clients, hooks, stores, chat pages, chat components — 5–8 days
3. **Implement the SSE streaming endpoint** — the `StreamingJob` model exists with no endpoint serving it
4. **Add HTTP-level tests** for the 13 Release 3 endpoints
5. **Add rate limiting and a content-length cap** to message creation
6. **Set a default page size** on `getConversationHistory`
7. **Update `docs/api.md` and `docs/database.md`** for Release 3
8. **Patch dev dependencies** to clear Dependabot

### Alternative: descope

If the launch date is immovable, launch Releases 1–2 only — auth, workspaces, projects, folders, assets, billing are complete, tested, and documented. Ship those, and hold Release 3 for a follow-up. This is a real option and it is honest; shipping a chat product with no chat UI is not.
