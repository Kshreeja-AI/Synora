# Synora AI - Database Schema Documentation

## Overview

Synora uses PostgreSQL 16+ with Prisma ORM for data management. All schema changes are version-controlled through Prisma migrations.

## Core Entities

### User
Represents a registered user in the system.

```prisma
model User {
  id            String      // Unique identifier (CUID)
  email         String      // Unique email address
  emailVerified DateTime?   // Email verification timestamp
  name          String?     // Display name
  image         String?     // Profile image URL
  password      String?     // Argon2id hash (null if OAuth-only); bcrypt
                             // hashes from before the R1 migration are
                             // transparently re-hashed to Argon2id on next
                             // successful login (see P0-11 doc)
  role          UserRole    // USER, ADMIN, MODERATOR
  status        UserStatus  // ACTIVE, INACTIVE, SUSPENDED, DELETED

  // Login lockout (R1-d): incremented on each failed password check,
  // reset to 0 on success. lockedUntil is set once the threshold is hit
  // (default: 5 attempts / 15 minutes, both config-driven) and cleared on
  // the next successful login.
  failedLoginAttempts Int
  lockedUntil         DateTime?

  // Relations
  accounts      Account[]   // OAuth accounts
  profile       UserProfile?
  preferences   UserPreferences?
  workspaces    WorkspaceMember[]
  projects      Project[]
  documents     Document[]
  images        GeneratedImage[]
  videos        GeneratedVideo[]
  audios        GeneratedAudio[]
  activityLogs  ActivityLog[]
  refreshTokens RefreshToken[]  // R1-c, see below
  
  // Timestamps
  createdAt     DateTime
  updatedAt     DateTime
  lastLoginAt   DateTime?
}
```

**Indexes**:
- `email` — no separate index declared; the `@unique` constraint already
  creates one, and a second explicit `@@index([email])` was removed
  during the post-Release-1 audit as pure duplicate write overhead (same
  reasoning applies to `Workspace.slug` below)
- `status`

### RefreshToken (R1-c, extended in Release 2 M3)
Backs the refresh-token rotation described in `docs/api.md`'s Auth
Endpoints section and `docs/production/R1-c_REFRESH_TOKENS.md`. Since M3
this row also doubles as the user-facing "session" — one row is one
signed-in device, which is what `GET /api/auth/sessions` lists.

```prisma
model RefreshToken {
  id          String    // Unique identifier — also the access token's `sid` claim
  tokenHash   String    // SHA-256 hash of the token — the raw opaque
                         // token is never stored, so a database read
                         // alone cannot mint a session
  userId      String    // FK to User, cascades on user delete
  expiresAt   DateTime
  revokedAt   DateTime? // Set on rotation (superseded) or explicit logout
  createdAt   DateTime
  lastUsedAt  DateTime  // Refreshed on rotation; drives "last active" in the session list
  userAgent   String?   // Captured at issue/rotation time; parsed into a display label server-side
  ipAddress   String?   // Captured at issue/rotation time
  rememberMe  Boolean   // Which expiry policy produced this row's expiresAt — display only
}
```

**Indexes**: `tokenHash` (unique), `userId`, `expiresAt`

### PasswordResetToken (Release 2 M3)
Same hash-at-rest discipline as `RefreshToken`: the raw token exists only
in the reset email link. Consuming one revokes every active session for
the user (see `docs/api.md`#reset-password).

```prisma
model PasswordResetToken {
  id        String    // Unique identifier
  tokenHash String    // SHA-256 hash — raw token never stored
  userId    String    // FK to User, cascades on user delete
  expiresAt DateTime  // Default 1h (PASSWORD_RESET_TOKEN_EXPIRY)
  usedAt    DateTime? // Set on consumption; single-use
  createdAt DateTime
}
```

**Indexes**: `tokenHash` (unique), `userId`, `expiresAt`

### Conversation & Message (Release 3 M1/M2)

The foundation of the chat platform: a workspace-scoped conversation
containing a tree of messages. The data model was established in M1;
M2 (Universal Conversation Engine) added `Conversation.lastMessageAt`
and the `StreamingJob` retry/error fields documented below, and is the
first milestone with a real service/API built on top of this model.

#### Conversation
```prisma
model Conversation {
  id            String              // Unique identifier (CUID)
  workspaceId   String              // FK to Workspace
  title         String              // Conversation title
  description   String?             // Optional longer description
  provider      String              // AI provider id used, e.g. "anthropic" —
                                     // a string, not an enum, matching the
                                     // ai/registry.ts descriptor pattern: adding
                                     // a provider never requires a migration
  model         String              // Concrete model name, e.g. "claude-sonnet-5"
  status        ConversationStatus  // ACTIVE, ARCHIVED, or DELETED
  isArchived    Boolean             // Convenience flag mirroring status
  isPinned      Boolean             // User-pinned for quick access
  lastMessageAt DateTime?           // (M2) Denormalized from the latest Message.createdAt —
                                     // avoids a correlated subquery for the default
                                     // "most recently active first" list sort. Null
                                     // until the first message is sent.
  folderId      String?             // FK to ConversationFolder (M12), optional

  // Relations
  workspace     Workspace
  messages      Message[]
  folder        ConversationFolder?
  tags          ConversationTag[]
  collaborators ConversationCollaborator[]
  versions      ConversationVersion[]
  activity      ConversationActivity[]
  shared        SharedConversation[]
  usage         ConversationUsage?
  toolCalls     ToolCall[]

  // Timestamps
  createdAt     DateTime
  updatedAt     DateTime
}
```

**Indexes:** `workspaceId` (workspace-scoped list queries),
`(workspaceId, createdAt)` (chronological listing),
`(workspaceId, lastMessageAt)` (M2 — the default list sort), `isArchived`
and `isPinned` (common list filters).

**State machine (M2):** `ACTIVE ⇄ ARCHIVED` via the service's `archive`/
`restore` methods; `{ACTIVE, ARCHIVED} → DELETED` via `delete` (terminal).
Enforced in `conversation.service.ts`, not just implied by the enum — each
transition is its own method that checks the current `status` before
proceeding, never a generic field update. See `docs/api.md`'s Conversation
Endpoints section for the corresponding routes.

**Deletion model:** `status: DELETED` is a soft delete — conversations
are never hard-deleted by application code, matching the `isArchived`
convention already used elsewhere in this schema. Deleting the parent
`Workspace` cascades (`onDelete: Cascade`), since a conversation cannot
meaningfully exist without its workspace.

#### Message
```prisma
model Message {
  id              String        // Unique identifier (CUID)
  conversationId  String        // FK to Conversation
  content         String        // Message text
  role            MessageRole   // USER, ASSISTANT, or SYSTEM
  parentId        String?       // FK to the message this replies to/branches from
  deletedAt       DateTime?     // Soft-delete marker — null means not deleted

  // Relations
  conversation    Conversation
  parent          Message?      // Self-relation ("MessageTree")
  children        Message[]     // Self-relation ("MessageTree")
  branch          MessageBranch?
  attachments     MessageAttachment[]

  // Timestamps
  createdAt       DateTime
  updatedAt       DateTime
}
```

**Indexes:** `conversationId` and `(conversationId, createdAt)` (message
timeline queries), `(conversationId, deletedAt)` (filtering out
soft-deleted messages), `parentId` (thread/branch reconstruction).

**Soft delete:** `deletedAt` follows the same nullable-timestamp
convention as `RefreshToken.revokedAt`/`WorkspaceInvitation.revokedAt` —
presence means deleted, the value is when. Added in M1 as schema-only;
`message.service.ts`'s `delete()` (M2) is what actually sets it — a plain
`UPDATE`, never a real `DELETE`, so the `parentId` self-relation's cascade
rule below never fires and a soft-deleted message's children are
unaffected.

**Threading:** `parentId` is a self-referential FK (`onDelete: Cascade`)
forming a tree, not a flat list — the root message of a conversation has
`parentId: null`. This is what lets Release 3 M8 (branching) attach
alternative responses at any point without restructuring the schema:
branching is "insert another child under the same parent," not a new
concept the base schema needs to accommodate later.

#### StreamingJob (Release 3 M2)
```prisma
model StreamingJob {
  id            String              // Unique identifier (CUID)
  conversationId String             // FK to Conversation (informational — no
                                     // formal relation declared, matching how
                                     // this model was originally scaffolded)
  messageId     String?             // FK-like reference to the assistant Message
                                     // this job produced — set only on success;
                                     // null while running or if every retry failed
  status        StreamingJobStatus  // PENDING, RUNNING, COMPLETED, FAILED, CANCELED
  attempt       Int                 // Generation attempts made so far (bounded by
                                     // StreamingRetryEngine — ai/streaming/statemachine.ts)
  lastError     String?             // The most recent failure's message, if any

  // Timestamps
  createdAt     DateTime
  updatedAt     DateTime
  completedAt   DateTime?
}
```

**Indexes:** `conversationId`, `status`.

**Purpose:** the per-generation state machine backing "retry support" and
"error recovery" — one row per attempted generation. It is created
`PENDING` when `messageService.enqueueGeneration()` enqueues the job, and
driven from there by `StreamingRetryEngine`
(`ai/streaming/statemachine.ts`) inside the `generate_response` worker:
moved to `RUNNING` before the first provider call, `attempt` incremented
before each retry, `lastError` updated after each failure, and finally
`COMPLETED` (with `messageId` set) or `FAILED`. The client follows the
same job over SSE while it runs, and can cancel it.

Release 3 also added a Universal Memory System, a Universal Tool Calling
Engine, and a Universal Search System — dozens of further models
(`Memory*`, `Tool*`, `Search*`) live in
`packages/database/prisma/schema.prisma` alongside the chat models above;
treat the schema file as the definitive source for their exact fields
rather than reproducing them here.

### Other models
The following exist in `packages/database/prisma/schema.prisma` and
aren't reproduced in full here — treat the schema file as the definitive
source for their exact fields:

- **`UserProfile`**, **`UserPreferences`** — one-to-one with `User`; bio/avatar/social links and theme/notification settings, respectively.
- **`WorkspaceMember`** — join table for the `User`↔`Workspace` many-to-many, carrying a `WorkspaceRole`.
- **`WorkspaceInvitation`** — pending email invitations to a workspace, token-based, with expiry.
- **`ApiKey`** — workspace-scoped API keys (not currently exposed via any route — reserved for a future programmatic-access feature).
- **`VerificationToken`** — generic identifier/token pair for NextAuth-style verification flows; not currently wired to any route.
- **`MessageBranch`**, **`MessageAttachment`** — one-to-one/one-to-many with `Message`: which sibling branch is "main" (Release 3 M8 branching), and file attachments on a message.
- **`ConversationFolder`**, **`ConversationTag`** — user-organizable grouping for conversations (nested folders; freeform workspace-scoped tags).
- **`PromptTemplate`**, **`ConversationTemplate`** — reusable saved prompts and full conversation starters, optionally workspace-scoped or public.
- **`AIMemory`** — one-to-one with `Workspace`; persisted assistant context/memory.
- **`SharedConversation`**, **`ConversationCollaborator`** — public share links (token, expiry, permission level) and per-user collaborator roles on a conversation.
- **`ConversationActivity`**, **`ConversationVersion`** — append-only activity/audit trail and content-version history for a conversation.
- **`Tool`**, **`ToolCall`** — workspace-scoped (or public) tool/function definitions and their per-conversation invocation log.
- **`ConversationUsage`** — one-to-one with `Conversation`; running token counts and estimated cost.
- **`StreamingJob`** — see "Conversation & Message (Release 3 M1/M2)" above; the AI Streaming Engine's (Milestone 3) per-generation job/state-machine row, one per attempted generation, driving retry and SSE progress.

## Relationships

### User → Projects (1:Many)
- A user can have multiple projects
- When a user is deleted, their projects are NOT deleted (preserved for archival)

### User → Content (1:Many)
- A user can create multiple documents, images, videos, audios
- When a user is deleted, content is soft-deleted

### Project → Content (1:Many)
- A project can contain multiple content items
- When a project is deleted, content is soft-deleted (not actually deleted)

### User → Workspace (Many:Many)
- Through `WorkspaceMember` table
- Allows multiple users per workspace and multiple workspaces per user

### User → OAuth Accounts (1:Many)
- A user can link multiple OAuth providers
- Handles: GitHub, Google, etc.

## Migration Workflow

Package manager is pnpm, not npm (see `packageManager` in the root
`package.json`). Run these from the repo root, or `cd
packages/database` first and drop the `--filter` flag:

### Creating a Migration
```bash
pnpm --filter @synora/database db:migrate:create --name description_of_change
```

### Applying Migrations
```bash
# Development — creates + applies + regenerates the client
pnpm --filter @synora/database db:migrate:dev

# CI / staging / production — applies pending migrations only, no prompts
pnpm --filter @synora/database db:migrate    # prisma migrate deploy
```

### Resetting Database (Development Only)
```bash
pnpm --filter @synora/database db:reset
```

### Inspecting Data
```bash
pnpm --filter @synora/database db:studio
```

Note: `db:generate` and `db:migrate` are also exposed as root-level Turbo
scripts (`pnpm run db:generate`, `pnpm run db:migrate`) that fan out to
every workspace package that defines them; `db:migrate:dev`, `db:reset`,
and `db:studio` are currently only defined in `packages/database`, so
those three need the `--filter` form above (or `cd packages/database`
first).

## Query Patterns

### Find User with Relations
```typescript
const user = await prisma.user.findUnique({
  where: { id: userId },
  include: {
    profile: true,
    preferences: true,
    workspaces: {
      include: { workspace: true },
    },
  },
});
```

### Get User's Projects with Recent Content
```typescript
const projects = await prisma.project.findMany({
  where: { userId: req.userId },
  include: {
    documents: {
      take: 5,
      orderBy: { createdAt: 'desc' },
    },
    images: {
      take: 5,
      orderBy: { createdAt: 'desc' },
    },
  },
  orderBy: { createdAt: 'desc' },
});
```

### Activity Log Query
```typescript
const activities = await prisma.activityLog.findMany({
  where: { userId: req.userId },
```

## Performance Considerations

1. **Indexes**: Created on frequently queried columns and foreign keys
2. **Pagination**: Always paginate list queries (avoid large result sets)
3. **Select**: Use `select` to fetch only needed fields
4. **Include**: Use `include` carefully, consider N+1 queries
5. **Batch Operations**: Use `createMany`, `updateMany` for bulk operations

## Backup & Recovery

Release 1 deliberately does not run its own backup job. Instead, choosing
a **managed** Postgres provider (RDS, Neon, Supabase, Railway, etc.) with
automated backups and point-in-time recovery enabled is a documented
production checklist requirement (`PROJECT_HANDOVER.md` §10) — the
provider's backup/PITR is the actual mechanism, not application code.
Owning an in-app backup job with a rehearsed restore drill is a Release 2
item (`RELEASE_2_PLAN.md`, R2-g).
