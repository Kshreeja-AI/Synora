### 1. ARCHITECTURE REVIEW

#### Issue 1.1: Rate Limiting Not Actually Implemented
**Severity**: 🔴 CRITICAL  
**Category**: Architectural Flaw

**Problem**:
The `rateLimitCsrfGeneration` middleware is defined but:
1. Never wired into any routes
2. Counts ALL tokens globally (not per IP)
3. Multiplies rate limit by 100 (`RATE_LIMIT_PER_MINUTE * 100 = 1000`)
4. No IP address stored in CsrfToken table for actual rate limiting

**Code Location**: `apps/backend/src/middleware/csrfProtection.ts:131-161`

**Risk**: 
- Attackers can enumerate tokens at 1000+/minute
- No actual per-IP rate limiting
- Brute force attacks on token space

**Recommendation**:
```sql
-- Add to CsrfToken model
ipAddress    String?      // Store IP of token requester
```

Add proper rate limiting:
```typescript
// Check tokens generated by THIS IP in last minute
const recentTokens = await prisma.csrfToken.count({
  where: {
    ipAddress: ip,
    createdAt: { gte: oneMinuteAgo },
  },
});

if (recentTokens >= CSRF_CONFIG.RATE_LIMIT_PER_MINUTE) {
  throw new ForbiddenException('Rate limit exceeded');
}
```

Wire middleware:
```typescript
router.get('/csrf', rateLimitCsrfGeneration, generateCsrfToken);
```

**Priority**: Fix before production

#### Issue 1.2: No Middleware Applied Globally
**Severity**: 🔴 CRITICAL  
**Category**: Architectural Gap

**Problem**:
CSRF middleware is only applied to `/auth/login`, `/auth/register`, `/auth/logout`. Any other state-changing endpoints added in future won't have CSRF protection unless developer remembers to add it manually.

**Risk**:

```typescript
// In backend server initialization
app.use((req, res, next) => {

    '/health',
    '/metrics',

    return next();

  csrfProtectionMiddleware(req, res, next);
});
```

Or use an explicit allowlist for protected routes:

```typescript
const PROTECTED_ROUTES = {
  'POST /auth/login': true,
  'POST /auth/register': true,

  'POST /users': true,
```

### 2. SECURITY REVIEW

#### Issue 2.1: Raw Token Stored in Database
**Severity**: 🔴 CRITICAL  
**Category**: Information Disclosure

**Problem**:
```prisma
model CsrfToken {
  token       String  @unique    // STORED RAW!
  tokenHash   String  @unique
}
```

The raw token is stored in the database. If database is compromised, attacker gets all valid tokens.

**Current Practice**: Bad  
**Best Practice**: Store only hash, discard raw token after returning to client

**Risk**:
- Database breach = all CSRF tokens compromised
- No audit trail without raw token storage
- Violates least-privilege principle

**Recommendation**:
Remove raw token storage:

```prisma
model CsrfToken {
  id            String    @id @default(cuid())
  // Remove: token         String  @unique
  tokenHash     String    @unique   // Only store hash
  userId        String?
  sessionId     String?
  createdAt     DateTime  @default(now())
  expiresAt     DateTime
  usedAt        DateTime?
  ipAddress     String?
  userAgent     String?   // For audit

  user          User?     @relation(...)
  @@index([tokenHash])
  @@index([userId, createdAt])
  @@index([expiresAt])
}
```

**Code Change**:
```typescript
// Store ONLY hash, never raw token
await prisma.csrfToken.create({
  data: {
    // token: newToken,  // DON'T STORE
    tokenHash: newTokenHash,
    expiresAt,
  },
});
```

**Priority**: Fix before production (security violation)

#### Issue 2.2: SessionId Field Never Populated
**Severity**: 🟠 HIGH  
**Category**: Incomplete Implementation

**Problem**:
```typescript
await prisma.csrfToken.create({
  data: {
    token,
    tokenHash,
    expiresAt,
    userId: (req as any).userId || null,
    // sessionId is never set!
  },
});
```

SessionId field in schema is never used. Tokens not tied to specific sessions, only users.

**Risk**:
- Token could be stolen and used from different session
- No session-level token binding
- Reduces CSRF token uniqueness guarantee

**Recommendation**:
Implement proper session tracking:

```typescript
// Get session ID from request
const sessionId = req.session?.id || req.sessionID;

await prisma.csrfToken.create({
  data: {
    tokenHash,
    expiresAt,
    userId: (req as any).userId || null,
    sessionId,  // Tie to specific session
    ipAddress: req.ip || req.socket.remoteAddress,
  },
});
```

Validate session matches on token consumption:

```typescript
// In middleware, verify token belongs to current session
if (csrfToken.sessionId && csrfToken.sessionId !== req.sessionID) {
  throw new ForbiddenException('CSRF token session mismatch');
}
```

**Priority**: Fix before production

#### Issue 2.3: No Token Invalidation on Logout
**Severity**: 🟠 HIGH  
**Category**: Session Management Gap

**Problem**:
When user logs out, their CSRF tokens remain valid in database until expiry (1 hour). If token is stolen before logout, it remains usable.

**Risk**:
- Stolen token remains valid after logout
- Attacker can perform CSRF after user leaves
- Violates session termination security model

**Recommendation**:
Invalidate all tokens on logout:

```typescript
router.post('/logout', csrfProtectionMiddleware, async (req, res, next) => {
  try {
    const userId = (req as any).userId;

    // Invalidate all CSRF tokens for this user
    await prisma.csrfToken.deleteMany({
      where: { userId },
    });

    res.json(createApiResponse({ message: 'Logged out successfully' }));
  } catch (error) {
    next(error);
  }
});
```

**Priority**: Fix before production

#### Issue 2.4: No CORS/Origin Header Validation
**Severity**: 🟠 HIGH  
**Category**: Missing Defense Layer

**Problem**:
CSRF middleware doesn't validate `Origin` or `Referer` headers. While token-based protection is primary defense, origin validation adds defense-in-depth.

**Risk**:
- No secondary check if token validation bypassed
- More vulnerable to confused deputy attacks
- Doesn't meet OWASP recommendations

**Recommendation**:
Add origin validation:

```typescript
function validateOrigin(req: Request): boolean {
  const origin = req.headers.origin || req.headers.referer;
  const allowedOrigins = [
    process.env.FRONTEND_URL || 'http://localhost:3000',
  ];

  if (!origin) {
    return false; // Reject if no origin header
  }

  return allowedOrigins.some((allowed) => origin.startsWith(allowed));
}

// In middleware
if (!validateOrigin(req)) {
  throw new ForbiddenException('Invalid origin');
}
```

**Priority**: Fix before production

### 5. TOKEN LIFECYCLE

#### Issue 5.1: Race Condition in Token Consumption
**Severity**: 🟠 HIGH  
**Category**: Concurrency Bug

**Problem**:
```typescript
// Line 43-65 of csrfProtection.ts
const csrfToken = await prisma.csrfToken.findUnique({
  where: { tokenHash },
});

// ... validation checks ...

// Check if already used
if (csrfToken.usedAt) {
  throw new ForbiddenException('CSRF token already used');
}

// Mark as used
await prisma.csrfToken.update({
  where: { id: csrfToken.id },
  data: { usedAt: new Date() },
});
```

**Race Condition**:
1. Thread A: Fetches token, checks usedAt (null)
2. Thread B: Fetches same token, checks usedAt (null)
3. Thread A: Updates token to used
4. Thread B: Updates token to used (succeeds!)
5. Both threads think they consumed unique token

**Risk**: 
- Token can be used multiple times with concurrent requests
- CSRF protection can be bypassed
- Race window: milliseconds, but exploitable

**Recommendation**:
Use database transaction:

```typescript
const result = await prisma.$transaction(async (tx) => {
  const token = await tx.csrfToken.findUnique({
    where: { tokenHash },
  });

  if (!token) throw new ForbiddenException('Token not found');
  if (token.usedAt) throw new ForbiddenException('Token already used');
  if (new Date() > token.expiresAt) throw new ForbiddenException('Token expired');

  // Atomic update within transaction
  return await tx.csrfToken.update({
    where: { id: token.id },
    data: { usedAt: new Date() },
  });
});
```

**Priority**: Fix before production (concurrency bug)

### 7. TIMING ATTACK RESISTANCE

#### Issue 7.1: Token Format Validation Before Comparison
**Severity**: 🟡 MEDIUM  
**Category**: Timing Attack Potential

**Problem**:
```typescript
// Line 35 in csrfProtection.ts
if (!CsrfManager.isValidTokenFormat(token)) {
  throw new ForbiddenException('CSRF token invalid');
}

// Line 40
const tokenHash = CsrfManager.hashToken(token);

// Line 43-44
const csrfToken = await prisma.csrfToken.findUnique({
  where: { tokenHash },
});
```

Early rejection on format validation reveals timing information:
- Invalid format: Fast rejection (< 1ms)
- Invalid token: Slow database lookup (5-10ms)

Attacker can differentiate between format errors vs. token not found.

**Risk**: Minor (token format is not secret), but violates constant-time principle

**Recommendation**:
Always proceed to token lookup even if format invalid:

```typescript
let csrfToken = null;
const tokenHash = CsrfManager.isValidTokenFormat(token) 
  ? CsrfManager.hashToken(token)
  : 'invalid-format-' + crypto.randomBytes(16).toString('hex');

csrfToken = await prisma.csrfToken.findUnique({
  where: { tokenHash },
});

// All paths now have consistent timing
if (!csrfToken || !CsrfManager.isValidTokenFormat(token)) {
  throw new ForbiddenException('CSRF token invalid');
}
```

**Priority**: Fix for defense-in-depth (low risk)

### 10. RACE CONDITIONS

#### Issue 10.1: Token Generation Creation Race
**Severity**: 🟡 MEDIUM  
**Category**: Concurrency

**Problem**:
In `csrfProtectionMiddleware`, after validating token, two operations happen:

```typescript
// Mark old token as used
await prisma.csrfToken.update({
  where: { id: csrfToken.id },
  data: { usedAt: new Date() },
});

// Generate new token
const newToken = CsrfManager.generateToken();
// ... create new token ...
await prisma.csrfToken.create({
  data: { ... },
});

// Return to client
res.setHeader('X-CSRF-Token', newToken);
```

If second create fails, token is lost but client has no new one.

**Risk**: User gets error but has no token for next request

**Recommendation**:
Use transaction:

```typescript
const result = await prisma.$transaction(async (tx) => {
  // Consume old token
  await tx.csrfToken.update({
    where: { id: csrfToken.id },
    data: { usedAt: new Date() },
  });

  // Create new token atomically
  const newTokenData = {
    token: CsrfManager.generateToken(),
  };
  
  const created = await tx.csrfToken.create({
    data: {
      tokenHash: CsrfManager.hashToken(newTokenData.token),
      expiresAt: CsrfManager.getExpiryTime(),
      userId: (req as any).userId || null,
      sessionId: req.sessionID,
      ipAddress: req.ip,
    },
  });

  return newTokenData.token;  // Return raw token to client only
});

res.setHeader('X-CSRF-Token', result);
```

**Priority**: Fix before production (atomicity)

### 11. API DESIGN

#### Issue 11.1: GET Endpoint Returns Token in Body (Not Secure)
**Severity**: 🟠 HIGH  
**Category**: API Design

**Problem**:
```typescript
// Line 115-121 in csrfProtection.ts
res.json({
  success: true,
  data: {
    token,  // Returned in response body
    expiresAt: expiresAt.toISOString(),
  },
});
```

Token returned in JSON response body. While HTTPS protects in transit, better to return in header:

```http
GET /auth/csrf
X-CSRF-Token: abc123...
X-CSRF-Expires: 2026-07-21T10:00:00Z

{
  "success": true,
  "data": {
    "expiresAt": "2026-07-21T10:00:00Z"
  }
}
```

**Risk**: Marginal (HTTPS provides protection), but violates best practice

**Recommendation**:
Return token in response header AND body:

```typescript
export async function generateCsrfToken(
  req: Request,
  res: Response,
  next: NextFunction
) {
  try {
    const token = CsrfManager.generateToken();
    const tokenHash = CsrfManager.hashToken(token);
    const expiresAt = CsrfManager.getExpiryTime();

    await prisma.csrfToken.create({
      data: {
        tokenHash,
        expiresAt,
        userId: (req as any).userId || null,
        sessionId: req.sessionID,
        ipAddress: req.ip,
      },
    });

    // Return in BOTH header (preferred) and body (fallback)
    res.setHeader('X-CSRF-Token', token);
    res.setHeader('X-CSRF-Expires', expiresAt.toISOString());

    res.json({
      success: true,
      data: {
        token,        // Fallback for clients that can't read headers
        expiresAt: expiresAt.toISOString(),
      },
    });
  } catch (error) {
    next(error);
  }
}
```

**Priority**: Improvement (low risk)

### 12. FRONTEND IMPLEMENTATION

#### Issue 12.1: Token Stored in SessionStorage (XSS Vulnerability)
**Severity**: 🔴 CRITICAL  
**Category**: Client-side Security

**Problem**:
```typescript
// Line 48-50 in useCsrfToken.ts
sessionStorage.setItem(CSRF_TOKEN_KEY, token);
sessionStorage.setItem(CSRF_EXPIRY_KEY, expiresAt.toISOString());
```

Token stored in `sessionStorage`, which is vulnerable to XSS attacks. If site has XSS vulnerability, attacker can read token:

```javascript
// In XSS payload
const token = sessionStorage.getItem('csrf-token');
// Send to attacker's server
```

**Risk**: 
- XSS + CSRF = account takeover
- If any part of site is XSSable, tokens are compromised
- sessionStorage is NOT protected from JavaScript

**Recommendation**:
Store token in memory-only (no persistence), but this creates problems with page refresh:

**Option 1: Memory Only (Best Security)**
```typescript
let cachedToken: string | null = null;
let cachedExpiry: Date | null = null;

export function useCsrfToken() {
  const [token, setToken] = useState<string | null>(null);

  useEffect(() => {
    // Check if we already have token in memory
    if (cachedToken && cachedExpiry && cachedExpiry > new Date()) {
      setToken(cachedToken);
      return;
    }

    // Fetch from server
    fetchCsrfToken().then((newToken) => {
      cachedToken = newToken;
      cachedExpiry = new Date(Date.now() + 60 * 60 * 1000);
      setToken(newToken);
    });
  }, []);

  return { token, ... };
}
```

**Option 2: httpOnly Cookie (Recommended)**
Backend sets token as httpOnly cookie:

```typescript
res.cookie('X-CSRF-Token', token, {
  httpOnly: true,           // JavaScript can't read
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'strict',
  maxAge: 60 * 60 * 1000,
});
```

Frontend reads from response header when needed:

```typescript
// Backend includes in response header
const csrfToken = response.headers.get('X-CSRF-Token');

// Or read from cookie (backend can set, frontend can't)
// Automatically sent by browser
```

**Priority**: Fix before production (XSS attack vector)

#### Issue 12.2: No Network Error Handling
**Severity**: 🟡 MEDIUM  
**Category**: Error Handling

**Problem**:

**Recommendation**:

```typescript
const [retryCount, setRetryCount] = useState(0);
const MAX_RETRIES = 3;

const initializeToken = async () => {
  try {
    if (isCachedTokenValid()) {
      // use cached
      return;
    }

    await fetchToken();
  } catch (error) {
    if (retryCount < MAX_RETRIES) {
      // Retry with exponential backoff
      setTimeout(() => {
        setRetryCount((r) => r + 1);
        initializeToken();
      }, Math.pow(2, retryCount) * 1000);
    } else {
      setState((prev) => ({
        ...prev,
        error: new Error('Failed to initialize security. Please refresh.'),
      }));
    }
  }
};
```

#### Issue 13.2: No Cleanup on Component Unmount

```typescript
      if (isMounted) {
        setState((prev) => ({
          ...prev,
          error,
          isLoading: false,

      }
    }
  };

  return () => {
    isMounted = false;  // Cleanup
  };
```

```typescript
      .post('/auth/login')
```

### 18. SCALABILITY

#### Issue 18.1: No Distributed Locking for Token Consumption
**Severity**: 🟠 HIGH  
**Category**: Multi-Server

**Problem**:
In multi-server deployment, race condition can happen across servers:

```
Server A: Fetches token, checks usedAt (null)
Server B: Fetches token, checks usedAt (null)  [both see null!]
Server A: Updates token to used
Server B: Updates token to used [both succeed!]
```

Without distributed lock or transaction across replicas, both servers mark token used.

**Risk**: Token reuse in distributed deployment

**Recommendation**:
Use database transaction (within single database, transactions are atomic):

```typescript
const result = await prisma.$transaction(async (tx) => {
  const token = await tx.csrfToken.findUnique({
    where: { tokenHash },
  });

  if (token?.usedAt) {
    throw new Error('Token already used');
  }

  return tx.csrfToken.update({
    where: { id: token.id },
    data: { usedAt: new Date() },
  });
});
```

If using multiple read replicas, ensure reads/writes go to primary:

```typescript
// Use primary connection only for CSRF validation
const result = await primaryDb.transaction(...);
```

**Priority**: Fix before production (distributed deployment)
